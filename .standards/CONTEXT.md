# Project Context

## Project Baseline

- Initial whole-repository brownfield audit for STANDARD cycle `integrate-actual-learning-progressions-20261001T162834Z-142f2df1`, established on 2026-10-01. No prior context, scope, design, or active implementation record existed. Repository HEAD at audit entry: `9d5c9a0` (STANDARDS installation). Entry working tree had only untracked `.standards/user-styles/`; no user style was selected or changed.
- Knowledge Graph for Education Global MCP is a curriculum-agnostic, deterministic, read-only FastMCP server. It discovers immutable framework snapshots, searches Academic Standards and Learning Components, retrieves hierarchy and provenance, and provides comparison evidence and client-side prompt workflows. It has no server-side LLM or MCP sampling.
- Six repository packages currently contain Academic Standards and Learning Components: Ghana English Basic 1–3, Ghana Mathematics Basic 4–6, India CBSE Science IX–X, India Tamil Nadu Mathematics Classes 1–5, Nigeria Mathematics Primary 1–3, and Rwanda Mathematics P1–P3. None includes Learning Progressions. `GraphType.LEARNING_PROGRESSIONS` exists as vocabulary, but `CapabilitiesService` explicitly lists `learning_progressions` as unavailable.
- The current progression tool/prompt is an evidence-collection and client-hypothesis workflow, not retrieval of stored progression relationships. The user requests its obsolete behavior/code be removed in favor of the supplied relationship artifacts. This audit changes only workflow coordination and context, and does not define the replacement surface.

## Stack and Tooling

- Python `>=3.13,<3.14`, package `kgfegmcp` version `0.3.1`, setuptools build backend, `src` layout, standalone `fastmcp==3.4.4`, Pydantic 2, pydantic-settings, Typer, and uv with `backend/uv.lock`.
- Local transport is STDIO; hosted transport is stateless Streamable HTTP using the same application factory. `backend/fastmcp.json` describes the factory; root `Dockerfile` includes source/config/packages and runs `kgfegmcp.http_server`.
- Quality tooling is configured in `backend/pyproject.toml`, `backend/.pylintrc`, `.pre-commit-config.yaml`, and GitHub Actions: pytest/asyncio/coverage, Black, isort, Ruff, mypy, pylint, interrogate, and secret detection. Ruff targets Python 3.13; Black/isort use 88 columns; interrogate has a 100% docstring threshold. MkDocs builds the project documentation.

## Structure and Boundaries

- `backend/src/kgfegmcp/app.py`, `bootstrap.py`, `config.py` — application factory, one shared immutable lifespan state, and configured input roots. Catalog, search, domain services, resources, and prompts reuse the accepted package runtimes rather than loading separate copies.
- `domain/`, `schemas.py` — typed identifiers, graph/epistemic vocabularies, frozen schemas, and rights contracts. `graph/` — package-local node/relationship indexes and bounded deterministic traversal.
- `packages/` — manifest/wire contracts, exact-byte checksums, construction, loading, decoding, semantic validation, and acceptance lifecycle. `catalog/` — accepted framework/snapshot discovery and package routing. Invalid-package behavior is configured as fail or quarantine.
- `profiles/` and `config/profiles/<id>/<version>/profile.json` — versioned framework interpretation, grade facets, statement types, hierarchy/cardinality, code search, rights, caveats, and optional progression heuristics. Curriculum-specific semantics belong here rather than Python branches.
- `search/` — package-local lexical, code, and component-tag retrieval. `services/` — ordinary framework, standard, learning-component, statistics, comparison, capabilities, and progression-evidence logic.
- `mcp/` — thin explicit tool/prompt/resource registration, protocol schemas/results, and error mapping. `resources/` — URI constructors, exact-artifact access, rights and size policy, derived documents, and provenance lookup. `prompts/` and `config/prompts/` — deterministic workflow rendering and optional per-framework overlays.
- `data/graph_packages/<framework>/<snapshot>/` — six terminal accepted package trees, each with a manifest, `delivery/`, and `detailed/`. `backend/tests/` — test infrastructure and a comparison query fixture, but no test modules in this checkout. `docs/` — reusable guides/reference/data/operations/development documentation. `cli/` — package build/validation, transport smoke, and MCPB distribution.

## Conventions and Constraints

- Preserve useful standards/components functionality, source terminology, exact framework/snapshot/package/node identity, all valid parent edges, multi-parent DAGs, and explicit unresolved status. Hierarchy, export order, code similarity, grade ordering, and lexical similarity do not establish progression, prerequisite, equivalence, or learner mastery.
- Accepted package bytes and referenced profile versions are immutable. Profiles are bound by ID/version/exact-byte hash. The package tree is closed: only the manifest and declared artifacts/directories are permitted; path escape, symlinks, missing/undeclared files, and case-insensitive collisions are rejected. A changed artifact set affects snapshot identity; builder refuses conflicting or terminal destinations.
- Backend README requires thin MCP adapters, ordinary services, full type annotations/docstrings, named arguments for multi-argument calls, alphabetical named arguments, no curriculum-specific Python branches, no package mutation, no server-side LLM/sampling, and STDIO logging on stderr.
- User constraints: server is publicly deployed; deployment/update execution remains user-owned and outside this cycle. Backwards compatibility for obsolete progression behavior is unnecessary. Teachers, ministry officials, and ed-tech organizations including EIDU, Pratham, Madhi, Trackosaurus, and Funda Wande are intended users. New functionality needs equivalent provenance, traceability, and explainability.
- User requests adaptation of existing machinery where feasible. Significant structural changes, if necessary, require simple explanations and recommendations from the responsible downstream roles. The best new tools/prompts/resources/workflows are unresolved scope questions, not Auditor decisions.
- Developer's first step must help copy relevant standards, components, and progression artifacts from the external results directory into this repository, to a temporary or permanent location. No source artifacts were copied during audit.
- No test may call live LLM APIs or paid services; mock such boundaries. Avoid introducing network-dependent acceptance fixtures.
- Both READMEs name root `instructions.md` as architectural/implementation source of truth, but it is absent. No instruction was inferred from that missing file. Actual `AGENTS.md`/`CLAUDE.md` contain only the STANDARDS integration block.

## Relevant Existing Behavior

- Delivery schema is `1.1`; source schema and manifest schema are `1.0`. Supported included graph types are Academic Standards and Learning Components. Recognized node labels are `StandardsFramework`, `StandardsFrameworkItem`, and `LearningComponent`. Accepted labels/types are only `hasChild` and `supports`; validator rejects other relationship types.
- Supports runs component → standard, references component identifier and standard CASE UUID, and has supportConfidence. Components remain separate from standards/hierarchy/search/statistics. Validator special-cases generated supports authorship; non-supports relationships currently inherit framework author/provider/attribution/license checks. LP attribution/author differs from that rule.
- GraphStore already indexes relationships by ID and by `(relationship label, endpoint)` for incoming/outgoing adjacency, preserving exact decoded records/source order. Direct navigation and GraphTraversal accept explicit relationship labels. Traversal is directed/DAG-oriented with bounds, cycle protection, deterministic output, completeness/truncation metadata, and separate root-path semantics. That existing machinery does not itself define symmetric related-item behavior or LP-specific public contracts.
- Search is exact normalized tokens or contiguous phrases, no semantic retrieval/stemming/synonyms. Code matching and grade/subject/statement-type facets are profile-governed. Client lexical expansion permits original wording plus at most three conservative alternatives with unchanged filters/bounds. Normalized grades are retrieval facets, not international grade equivalence.
- The obsolete progression touchpoints are `services/progression.py`, `services/progression_models.py`, `mcp/tools/progression.py`, `mcp/prompts/progression.py`, `bootstrap.py`, service exports, tool/prompt registration, capabilities/smoke inventories, `prompts/service.py`, `prompts/definitions.py`, and `prompts/models.py`. Profile `progressionHeuristics` exists and is empty in all six profiles; all six prompt configs have `inferredProgressionHypothesis` overlays. Documentation includes `docs/guides/progression.md`, `docs/reference/progression-tool.md`, prompt/profile references, and README descriptions. Other `llm_inferred` uses describe LC generation and comparison, so occurrence of that term alone is not proof of obsolete progression behavior.
- `collect_progression_evidence` accepts explicit grade scopes, topic/exact-standard focus, and a candidate limit of 2–20; it discovers/deduplicates standards, balances selected candidates by scope, and returns hierarchy evidence, truncation/exclusions and coverage warnings. It neither reads LP edges nor infers them. `inferred_progression_hypothesis` invokes this tool once, then instructs the client to propose labeled generated transitions; it can retrieve LCs through existing standard-to-component support links.
- Other prompts cover study support, teacher guides, handbooks, multigrade lesson planning, administrator alignment, and cross-framework comparison. Multigrade planning uses shared LCs across grades and refuses packages without components. These useful workflows share evidence/disclosure logic; their exact interaction with retained LP edges is Scoper/Architect-owned work.
- Resources expose catalog/framework, manifest, validation, unresolved evidence, profile, manifest-declared artifacts, standards/components/provenance, standard-component links, and exact package-local relationship lookup. No relationship-provenance URI or LP-specific resource currently exists. Standard provenance selects an item entry by CASE UUID; LC provenance has its own artifact lookup. Resource metadata includes canonical URI, exact package/profile identity, content byte count/hash, representation and source-artifact hashes. Rights/full-text/bulk/size policy is enforced independently of file presence; additional artifacts fail closed until explicitly assigned an exposure policy.
- Builder currently recognizes AS/LC detailed artifacts and requires `as_lc_nodes_<suffix>.jsonl` / `as_lc_relationships_<suffix>.jsonl` delivery filenames. Manifests/counts/validation reports have LC-specific fields and no LP-specific contract. Adding a raw sidecar or merely enabling a graph-type enum would not make LP data accepted or publicly available under the present implementation.
